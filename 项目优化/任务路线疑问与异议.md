## 1. 私有研究项目 × 共享知识库的悬空引用问题（最重要）

**现状**

- 第一轮明确：公共知识库对所有登录用户开放增删改，且不落 `owner_id`、
  不迁移目录（见《用户体系与数据隔离设计》§9、§10）。
- 论文研究的数据模型（ResearchProject / PaperRecord / EvidenceCard /
  ComparisonItem / ResearchReport / Citation，见《论文研究助手产品与功能
  架构》）是用户私有资源，其论文与证据必然引用公共知识库的文件和片段。

**问题**

任何登录用户都可以删除知识库文件或重建向量库。一旦删除或重建，其他用户
研究项目里的 PaperRecord / EvidenceCard 指向的来源就悬空：证据卡片可能
显示不出引文原文，报告引用无法回溯，研究数据被别人的操作破坏。

**影响**

- 违背"研究以证据与引用为中心"的产品定位：证据本身不可靠了；
- 属于跨用户副作用，性质上接近第一轮花大力气防住的越权问题，只是路径
  从"读取别人的会话"变成"破坏别人的证据"。

**建议**

- 017 设计数据模型时，让 **EvidenceCard 保存逐字引文快照 + 来源元数据**
  （原文文本、文件名、片段/页码标识、采集时间），知识库来源 ID 只作溯源
  线索，不作为渲染和校验的唯一依赖；
- 知识库文件被删除时，研究侧证据仍完整可读，只在 UI 标注"来源文件已
  不在知识库"；
- 是否反向限制（有研究项目引用的知识库文件禁止删除）不建议做——与
  "公共知识库人人可写"的第一轮原则冲突，快照方案代价更小。

**需要决策的点**

1. 017 是否按"证据快照"落库？（建议：是）
2. 快照文本与用户私有数据同等对待（备份、隔离、测试范围）。

## 2. "论文研究"意图的路由缺口由哪个任务补、怎么补

**现状**

- 《论文研究助手产品与功能架构》设想 FastJev 识别研究意图后引导用户进入
  研究项目；
- 但 012 的意图集只有 `general / unknown / kb_search / single_tool /
  complex`（`intent_router/schemas.py`），015 总图也只有四个执行分支，
  没有研究分支（仅在 `smart_conversation/graph.py` 顶部注释留了扩展点）。

**问题**

1. 任务归属不明：新增研究意图 + 总图研究分支，是放进 017，还是阶段 B
   的后续任务？017 若只做数据模型与 CRUD，路由入口就没人管；
2. 实现方式有风险：**给 fastjev 意图头新增一个意图类不是小改动**。
   2026-10-08 的 fastjev vs llm 对比测试中，联网搜索误判的根因就是意图
   头与工具头矛盾，最后靠工具头提升/托底规则才让 fastjev 达到 31/31。
   新增意图类会重新扰动这个平衡，且需要重新标注与回归。

**建议**

- 研究意图初期**不动 fastjev 意图头**：只走 LLM 路由或规则判定（例如
  关键词 + 项目存在性检查），验证产品路径后再评估是否进 fastjev；
- 明确"引导进入项目"不一定要新增 path：可以先用 RouteResult 的
  summary/候选信息在 direct_answer 里输出引导文案，真正的研究执行留在
  项目 UI 内触发，而不是让总图直接执行研究任务；
- 无论放哪个任务，任务文档必须写清意图集是否扩展、RouteResult 契约是否
  变化、012/015 的回归测试范围。

**需要决策的点**

1. 路由入口放在 017 还是独立任务？（建议：独立任务，017 保持纯数据层）
2. 研究意图首版是否只用 LLM/规则、不进 fastjev？（建议：是）

## 3. 017 必须显式继承隔离底线，不能默认沿用

**现状**

AGENTS.md 的底线——身份只来自服务端认证上下文、资源 ID 不是权限、
未登录 / 令牌过期 / 禁用用户 / 跨用户访问必须有自动化测试——目前只在
聊天域（003、006）逐条落实过。

**问题**

研究项目是全新的私有资源域（项目、论文记录、证据、报告各有自己的 ID）。
如果 017 文档只写"建表 + CRUD"，很容易复现第一轮防过的错误：按 ID 直查、
相信请求体里的 user_id、越权返回 200/403 而非 404。

**建议**

017 任务文档把以下条目逐条写进验收标准（与 003 同等强度）：

- 所有研究资源表带 `owner_id`（或经项目继承），Repository 查询必须带
  owner 条件；
- 当前用户一律来自服务端认证依赖，请求体 `user_id` 不参与授权；
- 跨用户访问统一 404，不暴露资源存在性；
- 未登录、令牌过期、禁用用户、跨用户四类场景有自动化测试。

**需要决策的点**

1. 子资源（证据、对比项、引用）是每张表带 owner，还是经 ResearchProject
   继承（同 message 经 conversation 继承的模式）？（建议：继承模式，
   与聊天域一致、改动小）

## 4. Streamlit 承载研究 UI（阶段 C）的适配性存疑

**现状**

- 阶段 C 计划研究项目 UI：项目列表、论文卡片墙、证据卡、对比表、报告
  编辑；
- 第一轮非目标明确写了"不替换前端框架"，现有 WebUI 全部是 Streamlit。

**问题**

卡片墙、可编辑对比表、长报告编辑这类高密度交互在 Streamlit 里实现会很
勉强：组件能力有限、每次交互整页 rerun、状态管理已经比聊天复杂一个量级
（015 的 WebUI 改动已经能感受到）。硬做可能产出体验很差且难维护的页面，
后期返工成本比现在决策更高。

**已核实的事实（2026-10-10）**

WebUI 已是纯 HTTP 客户端：`webui_pages/utils.py` 的 API 类通过 httpx 调
FastAPI（含 SSE 流式转换），Streamlit 只是后端 API 的一个消费者。因此
"为部分模块更换前端"在架构上可行，不构成后端重构前提。

**建议：渐进式，不做整体重构（2026-10-10 与用户讨论后细化）**

- 决策不必现在做：017（数据模型）与阶段 B（研究循环）均为纯后端，前端
  决策的 deadline 是阶段 C；
- **反对大爆炸重写**：最难迁移的是聊天 UI（SSE 流式、取消、Agent 时间线、
  附件、换用户状态清理），且第一轮隔离测试绑定 Streamlit 状态清理逻辑，
  重写没有产品收益只有回归风险；
- 推荐路径：阶段 C 为研究模块单独做一个轻量前端（如 Vue3/React SPA，由
  FastAPI 托管静态文件、同源部署），聊天与知识库暂留 Streamlit；研究 UI
  本质是 CRUD + 卡片 + 表格 + 文档预览，SPA 规模可控。产品路径验证成立
  后再决定是否把聊天/KB 也迁移（或永不迁移）；
- 若希望进一步压缩成本，可先做降级版过渡：阶段 C 首版仍用 Streamlit 的
  简化交互（列表 + 详情表单 + 只读对比表 + Markdown 报告预览）验证产品，
  随后再上独立 SPA；
- 必须诚实面对的成本：引入 node/npm 构建链（项目目前是纯 Python）、双
  前端的登录与导航统一、静态托管部署方式、前端测试方式从零开始。

**对 017 的直接影响**

研究模块 API 必须 API-first 设计：完整 REST + 流式事件契约，不夹带任何
Streamlit 特有假设，使前端决策可以安全推迟到阶段 C 而不返工。

**需要决策的点**

1. 阶段 C 用独立 SPA，还是先 Streamlit 降级版过渡再 SPA？
   （建议：先降级版验证产品路径，产品成立后上独立 SPA）
2. 017 是否按 API-first 契约设计研究模块接口？（建议：是）

## 附：前端重构与桌面化技术选型（2026-10-10 补充讨论）

用户补充了产品意向：后续想做**本地 agent / 桌面版**。选型分两层：

**前端框架（决定页面能否桌面化复用）——已定：React（2026-10-10 用户拍板）**

- **React 18 + Vite + TypeScript + Tailwind + shadcn/ui**；
- 判据：桌面 agent 终局必然带聊天 UI，React 的 LLM 聊天前端生态
  （流式渲染、Markdown、agent 时间线组件）现成最多；
- HTMX 服务端渲染过渡方案在桌面目标下不推荐（桌面壳内整页刷新体验差），
  Vue 方案随之作废。

**桌面壳（打包形态）**

| 壳 | 特点 | 定位 |
|---|---|---|
| Tauri 2 | Rust 壳 + 同一套 SPA，Python 后端可作 sidecar，包小 | 终局推荐 |
| Electron | 生态成熟、无 Rust，包大内存大 | 备选 |
| pywebview | 纯 Python 壳 + 同一套 SPA，一周可出原型 | 快速验证 |

**架构前提（关键）**

模型推理在实验室 GPU 上，用户桌面机器通常无 GPU，因此桌面版按
"壳 + 远程后端（连实验室 FastAPI）"设计，保留"壳 + 本机 sidecar
（PyInstaller/conda-pack 打包 FastAPI）"的可能性。由此现在就要定死：

- API base URL 可配置；
- SSE 用 fetch + ReadableStream 读取（EventSource 不能带 Authorization 头）；
- Bearer Token 存储不依赖浏览器 cookie；
- 研究模块不再向 Streamlit 添加任何新逻辑（strangler：SPA 挂 /research，
  Streamlit 原样保留，聊天页将来在 SPA 内重做，SSE 契约复用 012/015）。

**建议路线**

1. 现在：按已定的 React SPA 做研究模块（API-first），FastAPI 托管静态
   文件，浏览器直接用；
2. 阶段 C 后：pywebview 或 Tauri 出首个桌面壳（连实验室服务器）；
3. 产品成立后：Tauri 正式化 + 聊天页迁入 SPA，后端不动。

引入 node/npm 与桌面打包均为基础设施级决策，需 Codex 单独立任务文档，
不得顺手做进 017。
