# 智能聊天记忆机制现状问题与优化设计方案

## 1. 文档定位

本文用于指导 Langchain-Chatchat 项目重构智能聊天和知识库对话的记忆机制。

本文不限定代码文件、模块边界或修改规模。实现者可以根据当前项目结构调整数据库、后端服务、LangGraph 状态、SSE 事件和前端页面，只要最终满足本文的功能规则和验收标准。

本文包含：

1. 当前记忆机制的实际运行方式；
2. 当前实现存在的问题；
3. 优化后的目标架构；
4. 会话上下文、摘要、长期记忆、召回和临时对话的详细规则；
5. 智能聊天、知识库对话和 Agent 调用的统一接入方式；
6. 前端功能与交互；
7. 异常降级、数据迁移和可观测性要求；
8. 人工验收测试用例。

## 2. 建设目标

优化后的记忆系统应解决三个不同问题。

```text
第一层：模型应知道当前会话最近说了什么。
第二层：长会话压缩后，模型仍应知道当前任务讨论到哪里。
第三层：经过用户确认的重要信息，可以在其他会话中被相关地召回。
```

最终形成以下三层结构：

| 层级 | 内容 | 作用范围 | 主要用途 |
|---|---|---|---|
| 最近原始消息 | 用户问题、助手回答 | 当前会话 | 保留最新细节和原话 |
| 会话工作记忆 | 主题、目标、结论、约束、待办、较早摘要 | 当前会话 | 保持长对话连续性 |
| 持久化记忆与项目上下文 | 用户偏好、稳定背景、项目决策、项目规则、长期目标 | 跨会话或项目内 | 按不同语义和注入策略复用已确认信息 |

必须遵守以下底线：

- 原始聊天记录不能因为摘要而被删除；
- 会话上下文不能默认泄漏到其他会话；
- 长期记忆必须属于当前用户；
- 自动提取可以发现潜在记忆，但只能写入独立的待确认候选库，不能直接形成正式长期记忆；
- 当前产品中的“无记忆对话”不能写入会话工作记忆、长期记忆或待确认候选；
- 模型实际使用的记忆必须能够被用户查看；
- 当前用户消息优先于摘要和历史记忆；
- 知识库回答中的客观事实仍以检索文档为依据。

“长期”只描述数据能够跨会话持续存在，不代表这些内容在产品语义上属于同一种记忆。用户偏好、用户背景、项目决策、项目规则和目标可以共用持久化基础设施，但必须具有不同的作用范围、召回方式、状态和冲突处理规则，不能全部作为普通相似度记忆模糊召回。

## 3. 当前记忆机制

### 3.1 当前三类数据

当前项目已经实现三类记忆数据。

#### 3.1.1 原始聊天消息

数据库保存用户问题和模型回答。前端重新进入会话时，可以展示完整聊天记录。

普通智能聊天在模型调用时只读取最近几轮已经完成的消息。知识库对话主要使用前端请求中携带的历史消息。

#### 3.1.2 会话上下文

每个会话拥有独立的上下文记录，主要字段包括：

```text
当前主题
当前目标
已确认事项
限制条件
待解决问题
较早内容摘要
摘要覆盖到的消息位置
```

当前结构化字段主要通过关键词和正则表达式从用户消息中提取。

#### 3.1.3 跨会话持久化信息

当前实现把多种跨会话信息保存在独立记忆表中，主要包括：

```text
个人偏好
稳定背景
已确认决策
项目规则
历史结论
待办和长期目标
```

这些信息支持个人范围和项目范围，并具有启用、停用、过期和被替代等状态。当前实现主要把它们当作同一类“长期记忆”处理；目标设计将进一步区分用户档案、项目上下文、项目规则和目标的不同使用策略。

### 3.2 当前每轮请求流程

当前实现实际上存在两条彼此独立的流程，不能把它们描述成一条串行流水线。

第一条是前端确认卡片流程。用户发送消息后，前端会异步调用 `POST /memories/intents` 检测“记住、忘记、以后默认”等显式意图。该调用与回答请求并行，既不属于后端模型调用流水线，也不会在检测阶段写入数据。用户点击确认后，前端再调用应用接口完成写入。

```text
用户发送消息
      ↓
前端独立调用 /memories/intents
      ↓
返回“记住/忘记”确认卡片
      ↓
用户选择范围并确认
      ↓
写入会话上下文或个人长期记忆
```

第二条才是模型回答流水线。它在智能聊天、知识库对话和 Agent 运行中都会调用后端 `auto_extract`：

```text
保存本轮用户消息
      ↓
执行 auto_extract 自动提取
      ↓
更新会话结构化上下文和摘要
      ↓
执行智能对话意图路由（确定性快速路径或 LLM 路由）
      ↓
读取个人偏好
      ↓
按关键词召回跨会话记忆
      ↓
读取会话上下文
      ↓
读取最近聊天记录
      ↓
组合 Prompt 并调用模型
      ↓
保存模型回答
```

显式“记住/忘记”命中时，`auto_extract` 当前会因为“需要确认卡片”的开关而直接返回；但是普通陈述仍可能被自动提取并直接写入长期记忆表。

这里的“智能对话意图路由”与前端 `/memories/intents` 不是同一个功能。前者决定本轮走直接回答、知识库、工具或 Agent 等业务路径，并可能调用 LLM；后者只用于生成记忆确认卡片。只要智能对话意图路由实际调用 LLM，就必须与最终回答、Agent 和后台摘要共享唯一的 LLM 生成容量。

### 3.3 当前自动提取通道

当前 `auto_extract` 是现状中一条非常重要、且不同于确认卡片的写入通道。

它具有以下行为：

- 在普通智能聊天、知识库对话和 Agent 运行中都会执行；
- 只分析本轮用户问题，不分析知识库文档，也不直接分析助手回答；
- 受用户的“自动提取”开关控制；
- 使用规则识别姓名、身份、研究方向、工作、项目、长期目标和回答风格；
- 命中后直接写入长期记忆表，来源标记为 `auto_extract`；
- 自动提取记录通常为 `confirmed=false`；
- 第三期的“一般历史会话结论”开关开启后，这些未确认记录可能参与跨会话召回；
- 当前所谓“临时对话”正常情况下会阻止该通道写入；本方案将该功能改名为“无记忆对话”。

例如用户只是陈述：

```text
我正在研究无线通信定位。
```

在自动提取开关开启时，系统可能直接写入：

```text
研究方向：无线通信定位
source = auto_extract
confirmed = false
```

这条记录不经过确认卡片。它与“用户明确说记住，并在卡片上确认”是两种不同的产品行为。

### 3.4 当前摘要方式

当前默认摘要不是大模型语义摘要，而是：

1. 读取未被摘要覆盖的较早消息；
2. 将用户问题和助手回答转换为文本行；
3. 拼接到已有摘要之后；
4. 截取前 4000 个字符。

结构化主题、目标、决定和约束主要依赖正则规则识别。

### 3.5 当前召回方式

当前长期记忆召回主要执行：

1. 按当前用户过滤；
2. 排除停用、过期和已被替代的记忆；
3. 根据用户开关过滤记忆类别；
4. 根据会话项目过滤项目记忆；
5. 还可能通过 `_mentioned_project_names` 对问题文本做项目名子串匹配，把命中的项目加入召回范围；
6. 使用中文二字片段、英文词和稳定主题键进行关键词匹配；
7. 按命中数量和重要性排序；
8. 选择少量结果注入 Prompt。

## 4. 当前实现存在的问题

### 4.1 最近消息窗口与摘要窗口之间存在空洞

普通聊天默认只读取最近 3 轮，但摘要逻辑把最近 12 条消息留在摘要之外。

因此会出现：

```text
较早部分 → 已摘要
中间部分 → 没有进入摘要，也不在最近 3 轮中
最新部分 → 作为原始消息传给模型
```

中间部分会从模型上下文中消失。

知识库对话的问题更加明显：前端每次基本只发送当前问题，后端没有统一从数据库读取最近历史。用户追问“刚才第二点是什么意思”时，模型可能看不到上一轮回答。

### 4.2 当前摘要不是语义摘要

当前摘要只是聊天文本拼接和截断，不能可靠处理：

- 主题变化；
- 新旧结论冲突；
- 已完成和未完成事项；
- 用户否定此前方案；
- 用户与助手共同确认的结果；
- 工具调用产生的重要结果。

### 4.3 摘要达到上限后会停止吸收新内容

系统先放旧摘要，再追加新内容，最后截取前 4000 字。当旧摘要已经达到上限，后续新内容全部位于截断范围之后，新内容无法再进入摘要。

### 4.4 重置会话上下文后旧内容会重新出现

当前重置只清空摘要和结构化字段，没有记录“从哪条消息之后重新开始”。下一轮更新时再次扫描全部历史，旧主题、旧结论和旧约束可能重新进入会话上下文。

### 4.5 编辑会话上下文会破坏增量摘要位置

用户编辑上下文后，旧摘要可能保留，但摘要覆盖位置被清空。下一次更新会从历史开头再次摘要，造成重复内容。

### 4.6 页面显示的召回记忆不一定是模型实际使用的记忆

模型生成时进行一次记忆召回；前端回答完成后又调用预览接口重新计算。

以下情况会导致结果不一致：

- 用户本轮关闭了记忆，但预览接口仍然查询到记忆；
- 回答完成后用户修改了召回开关；
- 回答完成后记忆被编辑、停用或删除；
- 项目空间在回答后发生变化；
- 记忆排序规则或数据状态变化。

### 4.7 已检测到一次性内容，但候选处理策略不正确

当前代码已经使用 `_ONE_OFF_RE` 检测“本次、这轮、暂时”等一次性措辞，并会把推荐范围降为个人范围，同时显示“措辞限定在当前会话”。

问题不是系统完全没有识别一次性内容，而是识别后仍把它保留在“值得保存为跨会话记忆”的候选列表中。产品语义前后矛盾：系统一方面知道它只属于当前会话，另一方面仍建议用户把它跨会话保存。

### 4.8 中文关键词召回容易遗漏真正主题

中文长句只取开头有限数量的二字片段。主题位于句尾时，可能完全不参与召回。

例如：

```text
请结合我们之前已经讨论并确认的内容，说明模型路由应该怎么实现。
```

关键词数量可能在句首耗尽，“模型路由”无法用于匹配。

### 4.9 当前上下文更新成本会随会话长度持续增加

当前结构化提取可能每轮重新读取并扫描会话全部消息。长会话越长，每轮处理越慢，累计成本接近平方增长。

### 4.10 失败被静默忽略

当前多个记忆步骤采用捕获全部异常后直接继续回答的方式。保证聊天不被阻断是正确的，但用户和管理员无法知道：

- 本轮摘要是否更新失败；
- 本轮记忆是否召回失败；
- 本轮是否降级为仅最近消息；
- 失败发生在哪个阶段。

### 4.11 自动提取绕过确认，与长期记忆可信边界冲突

当前 `auto_extract` 会把普通陈述直接写入长期记忆表，只是用 `confirmed=false` 标记为未确认。第三期又允许用户打开“一般历史会话结论”开关，从而召回这些未确认记录。

这带来几个问题：

- 用户可能不知道自己的普通陈述已经被持久化；
- 规则误识别会形成错误长期记忆；
- “长期记忆必须由用户确认”的产品承诺与实际行为不一致；
- 自动记录和用户确认记录混在同一记忆列表中，状态语义不清楚；
- 用户打开一般历史召回后，模型可能使用用户从未确认过的推断。

这不是简单的代码错误，而是必须明确的产品取舍：保留“自动发现信息”的能力，还是保留“自动直接形成长期记忆”的能力。本文在后续方案中明确选择前者。

### 4.12 项目名子串匹配会造成静默越界召回

当前 `_mentioned_project_names` 会通过 `name in text` 判断问题中是否提到了某个项目。项目名如果是“记忆”“定位”等常见词，普通问题也可能被当成点名项目，进而读取用户没有主动选择的项目记忆。

问题不在于用户永远不能通过自然语言点名项目，而在于系统不能仅凭子串命中就静默扩大记忆范围。项目切换属于有权限和语义影响的上下文变更，必须由会话绑定或用户确认来完成。

### 4.13 现有能力与本次改造边界

本次改造不是推倒重来。以下矩阵用于区分“保留并回归验证”和“需要新增或修复”的内容：

| 能力 | 当前状态 | 后续动作 |
|---|---|---|
| 敏感内容服务端拒绝 | 已完成 | 保留现有实现，纳入回归测试 |
| 按用户过滤记忆 | 已完成 | 保留，确保过滤先于相关性排序 |
| 停用、过期、被替代记忆过滤 | 已完成 | 保留并回归；当前状态可能由多个字段计算，不强制重建为单一状态列 |
| 冲突处理与修订链 | 已完成 | 保留现有实现和历史数据 |
| 项目隔离主体 | 基本完成 | 保留会话绑定逻辑，删除项目名子串静默召回通道 |
| `use_memory=false` | 已完成 | 保留“只跳过偏好和跨会话召回、仍使用当前会话上下文”的语义 |
| v14/v15 数据迁移 | 已完成 | 不重复施工，在其基础上追加 v16 |
| `memory_usage_manifest` | 未实现 | 最高优先级新增，不能用回答后的二次查询代替 |
| 摘要与最近消息覆盖 | 有缺陷 | 修复空洞、截断方向、编辑和重置边界 |
| 知识库最近历史 | 有缺陷 | 统一改为从数据库读取 |
| 自动提取可信边界 | 与产品承诺冲突 | 改为独立候选库，确认后才创建正式记忆 |
| LLM 生成资源协调 | 调用分散在意图路由、聊天、RAG、Agent 等路径 | 建立全平台生成池并发 1；Embedding 独立限流 |
| 真正的临时存储 | 未实现 | 当前先改名“无记忆对话”，真正临时对话后续单独建设 |

## 5. 优化后的总体架构

建议引入统一的“上下文构建器”。智能聊天、知识库对话和 Agent 运行都调用同一套入口。

```text
                       ┌────────────────────┐
用户问题 ────────────→ │ 统一上下文构建器   │
                       └─────────┬──────────┘
                                 │
             ┌───────────────────┼───────────────────┐
             ↓                   ↓                   ↓
      最近原始消息        会话工作记忆        长期记忆召回
             │                   │                   │
             └───────────────────┼───────────────────┘
                                 ↓
                        上下文包 Context Package
                                 ↓
                     智能聊天 / RAG / Agent 模型
                                 ↓
                        记忆使用记录与回答
```

统一上下文构建器输入：

```text
user_id
conversation_id
message_id
当前问题
对话类型
项目空间
是否使用个人记忆
是否使用跨会话记忆
模型上下文预算
```

统一输出：

```text
个人偏好段
跨会话记忆段
会话摘要段
最近原始消息
本轮实际使用记忆清单
本轮上下文状态
```

所有对话入口必须使用同一个构建结果，不能由普通聊天、RAG 和 Agent 分别实现三套规则。

## 6. 最近原始消息设计

### 6.1 使用 Token 预算，不使用固定消息条数

最近原始消息应按 Token 预算保留，而不是固定“最近 3 条”。

建议初始规则：

```text
模型总上下文预算
- 平台系统提示词
- 工具说明预算
- RAG 文档预算
- 回答预留预算
= 可用于记忆和聊天历史的预算
```

可用于记忆和历史的预算再分配：

```text
最近原始消息：优先，约 50%～65%
会话摘要：约 20%～30%
个人偏好和长期记忆：约 10%～20%
```

具体数值应配置化，但必须保证最近原始消息优先于历史摘要和长期记忆。

该功能的前置条件是为每个可选模型提供可查询的上下文配置，至少包括：

```text
model_id
max_context_tokens
max_output_tokens
system_and_tool_reserve_tokens
rag_reserve_tokens
```

上下文构建器必须根据本轮实际模型读取配置并计算预算。当前模型列表只有模型名称、没有上下文长度时，不能假装已经实现动态 Token 预算；OpenAI 兼容网关也不一定能够返回真实上下文上限，因此模型上下文长度首先由平台人工维护配置表。

Token 计数规则必须明确：

1. 能获得目标模型官方或本地 tokenizer 时，使用对应 tokenizer；
2. 无法获得 tokenizer 时，使用经过该模型样本校准的保守估算，并预留安全余量；
3. 不能把某个固定的“中文字数换算系数”当成所有模型的精确值；
4. 估算不确定时优先少放历史，不能冒险超过模型上下文窗口；
5. manifest 必须记录计数方法和上下文上限来源。

建议记录：

```text
token_count_method：model_tokenizer / calibrated_estimate / default_estimate
context_limit_source：model_config / gateway / default
safety_margin_tokens
```

### 6.2 摘要与最近消息必须无缝衔接

必须满足不变量：

```text
摘要覆盖范围 + 最近原始消息范围 = 当前有效会话历史
摘要覆盖范围 ∩ 最近原始消息范围 = 空集
```

不能存在既没有进入摘要、也没有以原文提供给模型的中间消息。

第一阶段不能等到完整模型 Token 配置上线后才控制 Prompt 大小。过渡期由统一 `ContextPackage` 计算唯一的历史分界，不再让 `HISTORY_LEN` 和摘要保护窗口分别决定两套边界：

```text
recent_history_max_chars = 6000（默认值，可配置）
recent_history_min_turns = 3（兼容旧 HISTORY_LEN，只作为下限）
summary_boundary = 最近原始消息中最旧消息之前的位置
```

构建规则：

1. 从最新完整问答轮开始向前选择，在字符预算允许时至少保留 `recent_history_min_turns`；字符硬上限优先于最小轮数，不能为了凑满 3 轮造成上下文溢出；
2. 在不拆散完整问答轮的前提下，累计字符数不超过 `recent_history_max_chars`；
3. 超过字符上限时优先移除最旧轮次，不截断最新用户问题；
4. 被移出最近窗口的内容必须在同一次构建中进入规则摘要，摘要成功推进覆盖位置后才能从原文窗口移除；
5. 如果单个最新问答轮本身超过字符上限，保留当前用户消息和回答尾部，并在 manifest 标记 `history_truncated=true`，不能静默超出模型上限；
6. `HISTORY_LEN` 不再直接控制数据库取数和 Prompt 注入，只映射为过渡期最小轮数，后续由模型 Token 预算完全替代；
7. `SUMMARY_THRESHOLD` 只作为“何时尝试更新摘要”的触发阈值，不再定义最近消息保护窗口。

确定性结构化摘要在第一阶段属于构建 Prompt 前的本地步骤，不占模型队列。若它异常失败且待移出的旧消息会导致字符预算超限，系统不得把全部历史强塞给模型：保留当前问题和最新可容纳的完整轮次，manifest 标记 `history_gap_due_to_degradation=true`，向用户显示记忆降级提示并记录故障。该状态属于异常降级，不满足正常完成标准，必须可观测和可重试；“无空洞”验收针对摘要正常工作的主路径。

`6000` 字符是第一阶段的保守默认值，不是所有模型的精确容量。管理员可以调低；在第四阶段模型上下文配置和 Token 估算上线后，由真实预算替代该字符上限。无论采用字符预算还是 Token 预算，“无空洞”与“不超限”必须同时满足，不能为了修复历史空洞把全部未摘要历史塞进 Prompt。

### 6.3 最近消息内容

最近消息应包含：

- 用户问题；
- 助手最终回答；
- 必要的工具执行结果摘要；
- RAG 回答的引用编号和来源摘要；
- Agent 最终结果。

不应直接长期保留进 Prompt 的内容：

- 大段工具原始日志；
- 完整网页正文；
- 完整知识库文档片段；
- 重复的 Agent Step 调试数据。

这些内容应转换为简短观察结果，原始详情仍可在运行记录中查看。

## 7. 会话工作记忆设计

### 7.1 会话工作记忆字段

每个会话维护：

```text
topic：当前主题
goal：当前目标
confirmed：已确认事项
constraints：当前约束
open_questions：待解决问题
completed_items：已经完成的事项
summary：较早内容的语义摘要
summarized_through_message_id：摘要覆盖到哪条消息
context_start_after_message_id：重置后从哪条消息之后重新建立上下文
version：上下文版本
updated_at：最后更新时间
```

目标状态下，每个结构化条目应保存附加信息：

```text
text
source_message_id
source_role
created_at
updated_at
locked_by_user
status
```

其中 `status` 可取：

```text
active
resolved
replaced
removed
```

这是功能要求，不强制实现者必须拆成独立关系表。第一阶段至少要保留现有用户锁定语义，并保证来源和锁定状态不会丢失；v16 应补齐 `context_start_after_message_id`、`version`、`completed_items` 和摘要执行状态等会话级字段。条目级字段可以使用结构化 JSON 或独立表实现，只要能够支持来源追踪、锁定、状态变化和后续迁移。

### 7.2 语义摘要与模型调用约束

当前平台的 LLM 生成能力同一时刻只能处理一个请求。这是本方案的硬约束，不得把 LLM 摘要描述为“免费并行”的后台任务。Embedding 使用独立资源池，详见 §14.4。

模型调用优先级必须是：

```text
用户正在等待的意图路由 / 智能聊天 / 知识库回答 / Agent / 学生研究 / 导师审核
>
用户手动触发的摘要更新
>
系统自动摘要、记忆整理和其他后台模型任务
```

在并发能力仍为 1 时：

- 自动摘要默认使用不额外占用模型请求的“确定性结构化摘要”，不得继续以原文追加后截取前 4000 字作为目标实现；
- 不允许在生成用户回答之前同步调用 LLM 摘要；
- 不允许在存在前台模型请求排队或运行时启动后台 LLM 摘要；
- 如果模型平台不支持可靠取消，自动 LLM 摘要默认关闭，避免后台摘要占住唯一模型通道；
- 用户手动点击“更新摘要”时，应明确显示该操作需要占用模型队列；
- 将来只有在提供可抢占调度、独立摘要模型或额外并发容量后，才能默认启用自动 LLM 摘要；
- 一个 Agent Run 内部的多次模型调用也受同一个并发限制，记忆功能不能额外并行发起模型请求。

不使用 LLM 时，确定性结构化摘要至少要维护 `topic / goal / confirmed / constraints / open_questions / completed_items / summary`，并遵守以下规则：

- 按消息角色处理用户原话、助手结论和工具结果，不把助手建议伪装成用户事实；
- 识别用户的确认、否定、替换、完成和重新打开，更新对应条目状态；
- 对重复条目去重，对冲突条目保留替换关系；
- 超过容量时优先删除最旧、最低价值内容，保留最新有效结论；
- 每次只处理新增且已经离开最近原始消息窗口的消息；
- 处理失败时不推进覆盖位置，也不覆盖旧的有效结果。

前端和接口必须如实标明摘要来源：

```text
规则摘要：确定性结构化压缩，不调用模型
模型摘要：由 LLM 完成的语义结构化压缩
```

结构化大模型摘要仍是后续质量升级，但不能以牺牲正常聊天可用性为代价。无论使用哪种方式，原文追加截断都不再被视为完成态。

摘要模型输入：

```text
已有摘要
新增待压缩消息
当前结构化上下文
用户手工锁定条目
```

摘要模型必须输出结构化 JSON，例如：

```json
{
  "topic": "智能聊天记忆系统重构",
  "goal": "完成三层记忆机制并通过验收",
  "confirmed": [
    "最近消息和摘要必须无缝衔接",
    "会话摘要不能自动升级为长期记忆"
  ],
  "constraints": [
    "当前阶段不做模型路由"
  ],
  "open_questions": [
    "摘要模型失败时如何降级"
  ],
  "completed_items": [
    "完成当前实现代码审查"
  ],
  "summary": "用户与助手讨论了现有记忆实现，确认当前主要问题是……"
}
```

服务端必须验证 JSON 结构、字段长度和条目数量。解析失败、请求超时或模型返回空结果时，不得覆盖原有有效摘要，也不得推进 `summarized_through_message_id`。

接入大模型摘要前必须明确配置：

```text
摘要模型
输入和输出 Token 上限
超时时间
失败重试次数
单次与单会话成本上限
失败后的降级策略
```

摘要模型与主回答模型可以不同，但必须可观测其调用次数、延迟和 Token 消耗。

如果后续启用 LLM 摘要，推荐流程是：本轮先使用已有摘要和最近原始消息完成回答；回答完成后将摘要任务放入低优先级队列。调度器只有在没有前台请求时才能执行。下一轮到来时，如果摘要尚未完成，应临时扩大最近原始消息窗口；只有在扩大窗口仍会超过上下文预算时，才允许执行有界的同步补齐或降级截断，并在 manifest 中记录原因。无论哪种路径，都不能产生摘要与最近消息之间的历史空洞。

### 7.3 摘要内容来源

摘要应同时处理用户消息和助手回答，但不同内容的可信级别不同。

规则如下：

- 用户明确表达的决定和要求，可以成为已确认事项或约束；
- 助手回答可以进入会话叙事摘要；
- 助手单方面提出的建议不能自动成为“用户已确认事项”；
- 用户随后明确同意的助手建议，可以成为已确认事项；
- 知识库文档内容可以进入“本会话讨论了什么”，但不能自动成为用户长期事实；
- 工具返回可以进入摘要，但应注明它是工具结果；
- 失败或未完成的工具结果不能被写成已经完成。

### 7.4 摘要触发条件

满足任一条件时可更新摘要：

- 当前历史 Token 超过最近消息预算；
- 距离上次摘要新增消息超过指定数量；
- 用户确认重要决定；
- 用户切换主要主题；
- Agent 完成一个多步骤任务；
- 用户手动点击“更新摘要”。

不要只根据固定消息条数触发。

### 7.5 增量更新

每次只处理：

```text
summarized_through_message_id 之后
且不属于最近原始消息窗口
的消息
```

成功后原子更新：

```text
结构化上下文
summary
summarized_through_message_id
version
updated_at
```

如果同一会话存在并发请求，应使用乐观锁避免后完成的旧任务覆盖新摘要：更新语句必须携带读取时的 `version`，只有版本仍一致时才能同时写入摘要、覆盖位置和新版本号；冲突时重新读取并按策略重试，不能无条件覆盖。该能力需要在 v16 迁移中补齐版本字段或等价的并发控制字段。

### 7.6 用户编辑

用户可以编辑：

- 当前主题；
- 当前目标；
- 已确认事项；
- 限制条件；
- 待解决问题；
- 摘要正文。

用户编辑后：

- 不得清空 `summarized_through_message_id`；
- 被用户编辑的条目标记为 `locked_by_user=true`；
- 自动摘要不能因为处理旧历史而覆盖锁定条目；
- 如果后续用户明确提出冲突的新要求，可以生成冲突提示，并以最新用户消息为当前执行依据；
- 不应静默删除用户手工编辑内容。

### 7.7 重置

重置会话上下文时：

1. 清空结构化上下文和摘要；
2. 保留原始聊天记录；
3. 将 `context_start_after_message_id` 设置为重置时最后一条消息；
4. 后续只从该消息之后重新构建会话上下文；
5. 不影响个人偏好和长期记忆；
6. 记录一次重置审计事件。

这样旧内容不会在下一轮自动恢复。

## 8. 长期记忆设计

### 8.1 长期记忆类型

“长期记忆”是持久化时间概念，不是单一业务类型。产品上必须拆分为四个语义域，即使底层暂时共用一张表，也不能使用完全相同的召回和注入策略：

| 语义域 | 类型 | 示例 | 默认范围 | 使用策略 |
|---|---|---|---|---|
| 用户档案 | preference | 默认中文、先给结论 | 个人 | 在用户开启偏好且与当前任务不冲突时稳定注入 |
| 用户档案 | background | 研究无线通信、使用 MATLAB | 个人 | 仅在与当前问题相关时召回，避免每轮堆入全部背景 |
| 项目上下文 | decision / conclusion | 项目采用 LangGraph；某研究方案已否定 | 项目 | 仅在会话明确绑定该项目后相关召回 |
| 项目规则 | project_rule | 项目禁止自动模型路由 | 项目 | 项目绑定后确定性注入，不依赖模糊相似度命中 |
| 目标管理 | long_term_goal / todo | 完成实验室知识平台；补充召回评测 | 个人或项目 | 仅注入 active 目标，并区分 active / completed / paused / abandoned |

其中：

- 用户偏好解决“如何回答”的问题，优先级低于当前用户本轮明确要求；
- 稳定背景解决“用户是谁、具备什么条件”的问题，只在相关任务中使用；
- 项目决策和结论解决“这个项目已经确认了什么”的问题；
- 项目规则属于确定性约束，只要项目已绑定且规则 active，就应进入项目上下文，不能因为关键词未命中而漏掉；
- 目标和待办是有生命周期的任务状态，不应被当作永久事实无限召回。

因此，类型字段不仅用于展示，也必须参与作用域过滤、注入策略、冲突处理和前端管理。

当前数据中 `long_term_goal` 已作为个人记忆类别存在，本次不为了名称统一而强制重写成新的 `kind`。目标记录继续使用 `category=long_term_goal`，项目待办可以使用 `kind=todo`，同时新增独立的 `goal_status`：

```text
active：当前正在推进
paused：暂时暂停
completed：已经完成
abandoned：明确放弃
```

`goal_status` 与正式记忆本身的 `enabled / expired / superseded` 状态不是一回事：前者描述目标进度，后者描述这条记录能否被系统使用。只有记录本身可用且 `goal_status=active` 的目标可以进入当前目标上下文。

### 8.2 状态模型

正式长期记忆只描述已经被用户确认并创建成功的记录，其业务状态应明确区分：

```text
active：已确认且当前生效
disabled：用户停用
expired：超过有效期
superseded：被新记忆替代
deleted：用户删除
```

只有 `active` 且未过期的记忆可以进入召回。

上述状态是产品语义，不要求当前数据库立即重建为单一 `status` 列。若现有实现通过 `enabled`、`expires_at`、`superseded_by`、删除标记等字段计算状态，应保留兼容，只需保证最终过滤行为一致。

`pending / accepted / rejected` 属于待确认候选的生命周期，不属于正式长期记忆状态。

### 8.3 记忆来源

每条长期记忆至少记录：

```text
owner_id
content
kind
scope
project_id
source_conversation_id
source_message_id
confirmed_by_user
confirmed_at
confirmation_source
importance
expires_at
goal_status（仅目标和待办使用）
supersedes
superseded_by
revision_version
created_at
updated_at
```

来源会话可以被删除，但长期记忆在用户明确保存后可以继续存在。此时界面应显示“来源会话已删除”，不能伪造会话名称。

### 8.4 自动提取功能的明确产品决策

本方案不删除自动提取能力，但改变自动提取结果的生命周期。

明确决定如下：

```text
自动提取负责“发现候选”
用户确认负责“形成有效长期记忆”
```

自动发现结果写入独立实体 `memory_proposal`，不能先写入正式 `memory` 表再依靠 `confirmed=false` 阻止召回。候选至少包含：

```text
proposal_id
owner_id
content
status：pending / accepted / rejected
source_type：explicit_intent / session_context / auto_extract
source_conversation_id
source_message_id
extraction_rule
recommended_kind
recommended_scope
recommended_project_id
recommended_target：session / personal / project
created_at
reviewed_at
created_memory_id
```

优化后的 `auto_extract` 行为：

1. 继续分析用户普通陈述中的姓名、研究方向、技术背景、回答风格、项目和长期目标；
2. 命中后只创建 `memory_proposal(status=pending)`，不创建正式 `memory` 记录；
3. 候选可以持久化，避免刷新页面后消失；
4. 候选必须记录来源会话、来源消息、提取规则和创建时间；
5. `pending` 候选不得进入任何模型 Prompt；
6. `pending` 候选不得参与普通召回、项目召回或“一般历史会话结论”召回；
7. 用户确认后创建新的正式 `memory` 记录，并把候选标记为 `accepted`、记录 `created_memory_id`；
8. 用户拒绝后把候选标记为 `rejected`，且不再对同一来源消息和同一提取规则重复提示；
9. “无记忆对话”和未来的真正临时对话都不创建候选；
10. 关闭自动提取后，不再产生新的自动候选，但不删除已有候选和已确认记忆。

确认卡片、会话上下文提升和自动发现三类入口共用同一个 `memory_proposal` 生命周期和“待确认记忆”中心，避免用户在三个地方处理同一类事情；但交互优先级不同：用户明确说“记住”时立即弹出确认卡片，会话结论在上下文面板提示提升，自动发现默认进入候选中心而不打断聊天。

“自动提取”开关的产品文案应改为：

```text
自动发现可能值得保存的信息
系统只生成待确认候选，确认前不会用于其他会话。
```

当前“一般历史会话结论”开关也需要重新定义：

- 它只控制已经由用户确认、类型为一般结论的 `active` 记忆；
- 它不再用于放行 `confirmed=false` 的自动提取结果；
- 未确认候选只能在“待确认记忆”区域出现。

现有历史数据无法可靠判断“某条未确认自动记忆过去是否被用户编辑过”。修订表只覆盖新版本之后的操作，不能用缺失的历史证据推断旧记录已经经过人工确认。为守住“只有用户确认的信息才能成为正式长期记忆”的边界，本次迁移采用确定性规则，不做不可验证的分类猜测：

1. `confirmed=true`：保留为正式 active 记忆；
2. `source=auto_extract AND confirmed=false`：复制为 `memory_proposal(status=pending)`，原正式记忆行停用或标记已迁移，不再参与召回；
3. 迁移必须保留原内容、来源、时间、旧记录 ID 和新候选 ID 的映射，并保证重复执行不会重复创建候选；
4. 待确认中心必须提供“全部确认”“全部忽略”“全部删除”以及逐条编辑后确认，降低一次性复核成本；
5. “全部确认”仍需向用户清楚说明这些内容来自旧版自动提取，确认后才批量创建正式记忆；
6. 用户确认候选时创建新的正式记忆，不得把旧行简单改成正式记忆表中的 `proposed` 状态。

从本版本开始，用户在记忆编辑器点击“保存修改”必须显式写入 `confirmed=true`、`confirmed_at` 和 `confirmation_source=user_edit`；仅切换启用状态、系统维护字段或后台修订不能自动视为用户确认。

### 8.5 进入长期记忆的方式

允许以下入口：

1. 用户明确说“记住”；
2. 用户在会话上下文中点击“保存为跨会话记忆”；
3. 用户在记忆管理页手工创建；
4. 系统提出候选，用户确认保存。

除用户在记忆管理页直接手工新建正式记忆外，其余需要确认的入口统一先创建 `memory_proposal`。候选被接受后，根据 `recommended_target` 写入当前会话上下文或创建个人/项目正式记忆，并记录候选与最终记录的关联。

禁止：

- 自动把整段会话摘要写入长期记忆；
- 自动把助手回答写成用户事实；
- 自动把知识库文档内容写入用户记忆；
- 从“无记忆对话”或真正的临时对话保存记忆；
- 未经用户确认保存系统推断的敏感信息。

### 8.6 候选提升规则

系统可以提出候选，但不自动保存。

应提出候选的内容：

- 明确长期偏好；
- 明确项目决策；
- 稳定技术背景；
- 多个会话可能继续使用的结论；
- 明确长期目标。

不应提出候选的内容：

- 包含“本次、这轮、暂时、今天”的一次性要求；
- 普通提问；
- 助手尚未被用户确认的建议；
- 知识库检索到的客观文本；
- 密码、密钥、令牌、银行卡号、身份证号等敏感信息。

### 8.7 冲突与修订

同一用户、同一范围、同一主题槽位出现冲突时：

```text
旧记忆：项目使用 MySQL
新记忆：项目已经改为 PostgreSQL
```

用户确认新记忆后：

- 新记忆状态变为 active；
- 旧记忆状态变为 superseded；
- 新旧记录建立替代关系；
- 默认召回只使用新记忆；
- 记忆详情页仍可查看完整修订链。

当前消息与历史记忆冲突时，本轮先以当前消息为准，但不能自动永久修改旧记忆。回答后可以提示用户是否更新长期记忆。

## 9. 长期记忆召回设计

### 9.1 召回前过滤

召回必须先执行权限和状态过滤：

```text
owner_id = 当前用户
status = active
未过期
未被替代
不在当前会话忽略列表
来源不是“无记忆对话”或真正的临时对话
符合个人或项目范围
符合用户召回开关
```

权限过滤必须在相关性排序之前完成。

### 9.2 项目范围

项目记忆只有以下情况可以召回：

- 当前会话已经绑定同一个项目；
- 或者用户明确在本轮选择该项目。

仅仅在问题中出现一个与项目名相同的普通词，不应自动跨项目读取记忆。普通聊天默认不使用任何项目记忆。

因此应删除 `_mentioned_project_names` 触发静默召回的通道。系统可以识别用户似乎提到了某个项目，并显示“是否切换到项目 X”的轻量提示，但在用户确认切换前不得读取该项目记忆。用户确实想使用某项目时，应通过会话项目选择器或该确认操作建立明确绑定。

### 9.3 混合召回

#### 9.3.1 过渡期关键词召回修复

在正式引入中文分词、BM25 和向量召回前，先修复当前“只取句首有限二字片段”的明显缺陷：

- 在完整问题上生成候选，不因达到句首 8 个片段就提前结束；
- 过滤“我们、之前、怎么、什么”等高频停用词；
- 优先保留“模型路由、长期记忆、知识库检索”等完整主题词；
- 候选数量上限配置化，默认可提高到 24，而不是写死为 8；
- 降低通用短二字片段权重，增加完整主题词和靠近明确提问位置的词权重；
- 记录最终使用的 `matched_terms`，便于定位错误召回和漏召回；
- 用“主题出现在长句句尾”的用例验证修复。

该修复不等于正式检索方案，只用于在不增加模型和新依赖的情况下先消除确定性缺陷。

#### 9.3.2 正式混合召回

建议采用：

```text
结构化主题键召回
+ BM25/中文分词关键词召回
+ 向量语义召回
          ↓
RRF 或加权融合
          ↓
轻量重排
          ↓
相关性阈值过滤
          ↓
最多 3～5 条
```

第一版可以先实现中文分词 + BM25，再接入 Embedding。不能继续使用“只取句首 8 个二字片段”的方式作为正式召回方案。

实施前必须完成以下技术选型和性能验证：

- 中文分词采用何种依赖，以及目标部署环境是否可安装；
- SQLite 是否稳定提供 FTS5；若不能，使用应用层 BM25 还是独立检索组件；
- Embedding 使用哪个模型、服务地址、超时和降级策略；
- 当前本地 BGE-M3 已占用 100% CPU 的情况下，针对“每轮请求都向量化”的吞吐和延迟基准测试。

在基准测试达标前，不能默认把 BGE-M3 接入每一轮请求；可以先上线中文分词与 BM25，并把向量召回作为可关闭能力。

### 9.4 召回评分

评分至少考虑：

- 与当前问题的相关性；
- 是否为用户明确确认；
- 记忆重要性；
- 是否属于当前项目；
- 更新时间；
- 是否与当前消息冲突；
- 是否已经在本会话中多次使用。

不能只因为重要性高就召回与当前问题无关的内容。

### 9.5 召回结果

每条召回结果包含：

```text
memory_id
content_snapshot
memory_version
kind
scope
project_id
source_label
reason
score
matched_terms
```

`content_snapshot` 表示回答生成时使用的文本。之后即使原记忆被修改，历史回答仍能准确显示当时使用的内容。

## 10. 模型上下文组织规则

建议按照以下逻辑组织模型输入：

```text
1. 平台系统规则
2. 当前任务/工具运行规则
3. 当前绑定项目的 active 项目规则
4. 个人偏好
5. 与当前问题相关的用户背景、项目决策、结论和 active 目标
6. 当前会话摘要与结构化上下文
7. 最近原始消息
8. 当前用户问题
9. 本轮知识库文档或工具观察结果
```

同时在系统指令中明确优先级：

```text
平台规则
> 当前用户本轮明确要求
> 最近用户原话
> 当前绑定项目的有效规则
> 当前会话已确认上下文
> 已确认的相关项目决策、结论和用户背景
> 用户长期偏好和 active 目标
> 较早会话摘要
```

如果项目规则属于平台或实验室强制政策，应提升到平台规则层；如果只是用户为项目保存的工作约定，则当前用户本轮明确修改后应触发“是否更新项目规则”的确认，而不是静默坚持旧规则。

知识库对话还应明确：

- 记忆只提供用户背景、项目背景和表达偏好；
- 客观事实必须由本轮检索文档支撑；
- 记忆不能冒充知识库引用；
- 记忆与知识库文档冲突时，应指出冲突并优先使用有引用的当前文档。

## 11. 每轮实际使用记录

这是记忆功能改造的最高优先级（P0）。历史回答如果生成时没有保存使用快照，后续无法准确补算；因此必须先于召回算法和 LLM 摘要升级落地。平台基础生成槽位可以与第一阶段 A 并行建设，但不能阻塞上下文正确性修复；高级优先级、后台抢占和跨进程调度更不能作为 manifest 落地的前置条件。

manifest 与统一上下文构建器属于同一个 P0 大阶段：第一阶段 A 先让唯一的 `ContextPackage` 返回真实使用组件，第一阶段 B 紧接着将这些组件固化为 manifest、SSE 和历史展示。两者可以拆成便于审核的连续提交，但第一阶段在 A、B 都完成前不能宣称整体交付，也不能在三条旧链路中分别实现临时快照。

### 11.1 生成时记录

模型调用前，统一上下文构建器生成 `memory_usage_manifest`：

```json
{
  "session_context_version": 7,
  "summary_through_message_id": "msg-100",
  "recent_message_ids": ["msg-101", "msg-102", "msg-103"],
  "preferences": [
    {"id": "mem-1", "version": 2, "content": "默认使用中文回答"}
  ],
  "recalled_memories": [
    {
      "id": "mem-9",
      "version": 1,
      "content": "项目采用 LangGraph",
      "reason": "与当前问题中的 LangGraph 架构相关"
    }
  ],
  "memory_disabled_for_turn": false,
  "degraded": false,
  "budget_source": "estimate",
  "generation_status": "prepared",
  "model_started_at": null,
  "model_finished_at": null,
  "failure_stage": null,
  "failure_reason": null
}
```

该记录应与模型输入使用同一份数据，不能在回答后重新查询推算。

`generation_status` 使用以下状态机：

```text
prepared → queued → started → completed
                         ↘ partial / cancelled / failed
queued → cancelled / failed
prepared → failed
```

在基础生成协调器尚未接入某条调用路径时，允许直接执行 `prepared → started → completed / partial / cancelled / failed`；`queued` 只在请求确实进入等待队列后写入，不能为了满足状态机而伪造排队状态。

manifest 在模型调用前保存的是“已准备的上下文快照”，只有模型真正开始生成后，才能描述为“模型实际使用过”。前端文案必须跟随状态：

- `prepared / queued` 且模型未启动：显示“上下文已准备，但模型未开始生成”；
- `started / partial / cancelled / failed` 且模型已经启动：保留快照，并说明未完成的回答使用过这些上下文；
- `completed`：显示“本轮实际使用了……”；
- 路由、排队、模型启动、流式生成等不同阶段失败时，分别记录 `failure_stage` 和经过脱敏的 `failure_reason`。

### 11.2 持久化与 SSE

要求：

- 将使用记录保存在当前助手消息的 metadata 中；
- 流式回答开始时发送记忆使用 SSE 事件；
- 前端把使用记录绑定到对应助手消息；
- 重新打开历史会话后仍可查看当时使用的记忆；
- 后续修改或删除记忆不改变历史消息中的使用快照。
- 后续写入回答、Agent 状态或引用信息时必须合并 metadata，不能整体覆盖并丢失 manifest；
- Agent 完成、失败、取消和恢复路径都必须保留同一份上下文快照及 manifest；
- manifest 必须在模型请求进入 `LLM_GENERATION` 池或直接开始模型调用前完成并持久化，不能等回答结束后补算。
- 智能聊天和知识库聊天的停止、超时、路由失败、排队取消及流式中断路径也必须更新状态并保留 manifest；
- 对 manifest、回答内容、引用、Agent 状态的后续 metadata 写入必须按字段合并，不能整体替换。

### 11.3 停止、取消和半截回答

用户停止流式生成、连接中断或模型超时后，只要已经产生可见文本，就必须保存当前文本，不能因为取消路径提前返回而让刷新后的回答变成空串。

未完成回答的产品规则：

- 原始文本照常持久化，并标记 `generation_status=partial / cancelled / failed`；
- 历史页面继续展示已有内容和“未完成”状态；
- 最近原始消息可以携带该内容，支持用户下一轮说“继续”，但注入 Prompt 时必须带 `[未完成回答]` 角色标记；
- 不得把未完成回答提取为 `confirmed`、`completed_items`、项目结论或长期记忆候选；
- 规则摘要和模型摘要都不得把未完成内容概括成已经完成的结论；
- 如果模型尚未开始且没有任何回答文本，只保存 manifest 和失败/取消状态，不制造空的助手结论。

### 11.4 SSE 事件兼容

新增 `memory_manifest`、生成状态等 SSE 元数据事件时，必须保证新旧消费者不会把元数据渲染成回答正文：

- React 前端应在通用 token 回退分支之前识别元数据事件；
- Streamlit 兼容入口必须显式忽略或处理元数据事件；
- 未识别的元数据事件默认忽略并记录调试日志，不能降级为 token；
- 元数据事件使用明确事件类型，正文内容字段保持为空，避免旧客户端误拼接；
- 旧消费者不支持新事件时，最多不展示记忆说明，不能污染模型回答；
- 智能聊天、知识库聊天、Agent 流式输出和非流式消费路径都要做兼容测试。

非流式响应不另造一套 manifest 查询流程：最终响应块的 metadata 必须携带与助手消息中相同的 manifest 和最终生成状态。知识库非流式路径消费完整生成器并返回最后一块时，该最后一块必须保留 metadata；如果响应协议支持顶层 metadata，也必须与消息持久化快照同源，不能回答后重新计算。

## 12. “本轮不用”和“当前会话忽略”

必须区分两个功能。

### 12.1 本轮不使用跨会话记忆

只影响当前请求：

```text
不使用个人偏好
不使用跨会话长期记忆
仍然使用当前会话上下文和最近聊天记录
```

下一轮恢复默认状态。

建议按钮名称：

```text
本轮不使用跨会话记忆
```

### 12.2 当前会话忽略某条记忆

用户在某条记忆上选择：

```text
在当前会话中不再使用
```

后续当前会话都不再召回该记忆，其他会话不受影响。用户可以在会话设置中取消忽略。

不要继续把这个功能称为“本次不使用”，避免用户误解为只影响一轮。

### 12.3 五层开关的作用范围和优先级

“不用记忆”不是一个布尔值。系统同时存在以下五层控制，前后端必须按同一优先级计算最终结果：

| 控制层 | 控制内容 | 持久化位置 | 作用时间 | 能否放宽上层限制 |
|---|---|---|---|---|
| 用户级总开关 | 是否启用跨会话记忆能力 | 用户设置 | 所有会话，直到用户修改 | 不适用，最高层总闸 |
| 用户级分类开关 | 偏好、决策、项目、一般结论等哪些类别可召回 | 用户设置 | 所有会话，直到用户修改 | 不能绕过总开关 |
| 会话级个人偏好开关 | 当前会话是否读取个人偏好 | 会话记录 | 当前会话持续生效 | 不能绕过用户总开关和偏好分类关闭 |
| 单轮 `use_memory=false` | 当前请求暂时不读取个人偏好和跨会话记忆 | 请求参数，不持久化 | 仅当前请求 | 只能收紧，不能开启任何已关闭能力 |
| 按条会话忽略 | 当前会话不使用指定记忆 ID | 会话忽略表 | 当前会话持续生效 | 不能被分类开关或单轮参数重新启用 |

最终判定顺序：

```text
用户总开关允许
AND 对应分类开关允许
AND（若为个人偏好）会话级个人偏好开关允许
AND 本轮 use_memory != false
AND 该记忆不在当前会话忽略列表
= 本轮可以使用
```

补充规则：

- 当前会话摘要和最近原始消息不是跨会话记忆，不受 `use_memory=false` 影响；
- 项目规则还必须满足当前会话明确绑定项目；
- “无记忆对话”禁止写摘要、候选和正式记忆，但是否读取既有个人偏好由会话级开关决定，默认关闭；
- 前端不需要把五层全部堆成同一排开关：用户级总开关和分类开关放在记忆设置，会话级开关放在会话设置，单轮开关放在发送区，按条忽略放在记忆使用详情；
- 接口返回最终生效状态及被哪一层关闭，避免前端只看本地开关猜测结果。

## 13. 临时对话设计

当前“临时对话”只是不写记忆，但原始消息仍然持久化，容易造成误解。

本期先修正产品承诺，后续再建设真正的临时存储。

### 13.1 本期：将当前功能改名为“无记忆对话”

当前实现必须统一改名为“无记忆对话”，其产品说明应明确：

- 会话和原始消息照常持久化；
- 会话仍出现在永久历史列表中，并显示“无记忆”徽章；
- 当前没有 TTL，也不会在关闭页面或退出后自动删除；
- 不生成会话工作记忆或摘要；
- 不创建正式长期记忆和 `memory_proposal`；
- 增加持久化的会话级 `use_personal_preferences` 设置；普通会话默认开启，“无记忆对话”默认关闭；
- 用户可以在会话设置中明确开启或关闭“读取个人偏好”，修改后对该会话后续请求持续生效；
- 单轮 `use_memory=false` 可以临时覆盖为关闭，但不能反向绕过会话级关闭；
- 是否读取现有个人偏好必须由界面开关清楚表达，不能暗示无痕。

单个请求临时关闭跨会话记忆的功能仍使用 §12.1 的名称“本轮不使用跨会话记忆”，不能与“无记忆对话”混为一谈。

### 13.2 后续：真正的临时对话

- 不写会话摘要；
- 不写长期记忆；
- 不允许“记住”；
- 默认不出现在永久会话列表；
- 原始消息只保存在临时会话存储中；
- 用户关闭页面或超过 TTL 后删除；
- 可以读取个人偏好，但必须提供“完全不读取记忆”开关；
- 临时对话不能作为长期记忆来源。

真正的临时对话需要独立或明确隔离的临时存储、TTL 清理任务和退出删除机制。在这些能力全部完成并通过验收前，界面不得使用“临时对话”“无痕对话”名称。

## 14. 智能聊天、知识库对话和 Agent 的统一接入

### 14.1 智能聊天

每轮从数据库加载最近原始消息，不依赖前端回传完整历史。

无论最终路由到：

- 直接回答；
- 单工具调用；
- 知识库任务；
- 多步骤 Agent；

都应复用同一份会话上下文和长期记忆结果。

### 14.2 知识库对话

知识库对话必须从数据库加载当前会话最近消息，并接入同一份会话摘要。

推荐流程：

```text
构建会话上下文
      ↓
根据当前问题检索知识库
      ↓
组织记忆、历史和文档
      ↓
生成带引用回答
```

检索文档不能触发“记住”或自动写入记忆。

### 14.3 Agent 运行

Agent 规划阶段可以读取：

- 当前会话目标；
- 当前约束；
- 最近消息；
- 相关项目规则。

每个 Step 不应重复执行完整记忆召回。一个 Agent Run 开始时固定上下文快照，并保存其 manifest：

- 普通 Resume 属于同一个 Run，必须复用原快照，不能因为恢复时间不同而悄悄换成新的长期记忆；
- Cancel 只改变运行状态，不能删除或覆盖原 manifest；
- 用户追加新指令时，可以创建新的上下文快照版本，并明确记录它与原 Run 的关系；
- Agent 的规划、判断、重规划和最终回答调用全部经过统一 `LLM_GENERATION` 池，任何时刻运行中的生成调用不得超过 1。

Agent 完成后，可以把最终结果纳入会话摘要，但不能自动保存为长期记忆。

### 14.4 模型资源池与统一调用协调器

当前平台的 LLM 生成能力同一时刻只能处理 1 个请求。这是已知基础设施约束，不以网关地址、远端模型通常是否支持并发或后续实测猜测为依据。与此同时，Embedding 与生成模型是不同类型的资源，不能用一个含糊的“模型并发数”混在一起。

资源必须分为两个池：

```text
LLM_GENERATION 池，max_concurrency = 1
- 使用 LLM 的意图路由；确定性快速路由不占用该池
- 智能聊天回答
- 知识库回答生成
- Agent 规划、判断、重规划和最终回答
- 学生研究模块的 LLM 调用
- 导师审核模块的 LLM 调用
- LLM 摘要、模型记忆整理等后台生成任务

EMBEDDING 池，独立配置并发、超时和限流
- 知识库查询向量化
- 文档入库向量化
- 记忆向量化
```

Embedding 不占用唯一的 LLM 生成槽位，但必须独立限流，避免本地 BGE-M3 或其他 Embedding 服务因并发过高拖垮机器。两类资源分别记录队列长度、等待时间、运行时间、超时和失败率。

当前仓库默认是单服务进程部署。因此协调能力分成“当前部署必须具备的基础协调”和“启用后台 LLM 或多 worker 前必须具备的高级调度”，不能让后者阻塞规则摘要和上下文修复。

当前部署的基础协调要求：

```text
max_concurrent_llm_generation_requests = 1
每次实际 LLM 调用各自入队一次
覆盖 async、run_in_threadpool 和 LangGraph 线程调用
启动时验证当前仍为受支持的单 worker 模式
等待、开始、结束、超时和失败写结构化日志
```

“每次实际 LLM 调用各自入队”意味着一个 Agent Run 可以多次排队调用模型，但任何时刻只有一次调用运行；不能把整个 Agent Run 只计作一次，也不能让 Agent 内部线程绕过协调器。意图路由如果走 LLM，也必须先进入同一生成池；只有规则命中的确定性快速路径可以直接返回。

基础协调器不能只使用一个只对单事件循环有效的 `asyncio.Semaphore(1)`，必须让 FastAPI 异步路径、同步 `run_in_threadpool` 路径和 LangGraph/Agent 线程共享同一个进程级容量控制。当前版本不要求为尚未启用的多 worker 部署预先建设分布式锁，但必须在启动配置和测试中拒绝未经支持的多 worker 模式。

容量获取点必须唯一放在 ChatModel/模型客户端调用层，覆盖实际 `_generate / _stream` 或等价的最终模型请求入口；路由、业务 Service、Agent Run 和 LangGraph 节点不得再在外层重复获取同一生成槽位。否则“外层 Agent Run 已持锁、内部模型调用再次取非重入锁”会造成自死锁。

调用级规则：

- 每次实际模型请求获取一次容量，流式调用从请求开始一直持有到流结束、取消或异常；
- 获取必须有明确超时，超时写入 `failure_stage=model_queue`；
- 释放放在调用作用域的 `finally`，正常、异常和取消都必须释放；
- 同一执行上下文的嵌套获取默认禁止并记录错误；若实现选择可重入机制，必须以调用上下文计数，只有最外层退出时释放；
- Agent Run 可以依次进行多次模型调用，每次分别获取和释放，不能整段 Run 长时间占有槽位；
- 前端在请求等待生成槽位时显示“正在等待模型资源”，不能表现为无反馈卡死。

以下能力放到真正启用后台 LLM 摘要或多 worker 部署之前完成，不作为第一阶段 A/B 的前置条件：

```text
前台请求优先于后台任务
后台任务排队、短超时和可取消
已经开始且不可可靠取消的请求不强行抢占
请求级取消和调用级状态追踪
多 worker 部署时的跨进程并发协调
```

记忆系统的上下文构建、关键词召回、候选生成和规则摘要在模型队列之外完成。只有真正需要 LLM 的步骤进入 `LLM_GENERATION` 池。

“前台优先”只对尚未开始的排队任务有效。如果一个后台摘要调用已经开始，而模型或网关不支持可靠取消，新到达的前台请求仍然只能等待。因此在高级调度完成并通过验收前，自动 LLM 摘要保持关闭；手动模型摘要必须使用短超时、小批量输入并显示排队状态，不能用“异步”掩盖它仍占用唯一生成通道。

## 15. 前端功能设计

### 15.1 会话上下文入口

聊天顶部显示：

```text
本会话上下文
```

展开后展示：

- 当前主题；
- 当前目标；
- 已确认事项；
- 限制条件；
- 待解决问题；
- 已完成事项；
- 较早内容摘要；
- 摘要类型：规则摘要 / 模型摘要；
- 摘要更新时间；
- 摘要覆盖到哪一条消息；
- 当前保留多少条最近原始消息；
- 本次摘要是否更新成功。

操作：

```text
更新摘要
编辑上下文
重置上下文
查看摘要覆盖范围
```

该面板需要独立的会话上下文状态接口，不能用某条回答的 manifest 临时推算。接口至少返回：

```text
context_version
summary_type：rule / llm
summary_updated_at
summarized_through_message_id
recent_message_count
last_summary_status：idle / queued / running / succeeded / failed
last_summary_error（面向管理员，普通用户只显示友好状态）
model_queue_required
```

用户手动点击“更新摘要”时，如果需要调用模型，页面必须显示“等待模型资源/正在更新”，不能让用户误以为该操作与聊天并行且不占资源。

### 15.2 每条回答的记忆使用说明

每条助手回答下方显示：

```text
本轮使用了 2 条个人偏好、1 条历史记忆和当前会话摘要
```

展开后显示：

- 记忆内容快照；
- 类型；
- 个人或项目范围；
- 来源会话和日期；
- 为什么召回；
- 当前状态；
- 本回答生成时的记忆版本。

操作：

```text
在当前会话中不再使用
停用
编辑
删除
查看修订历史
```

### 15.3 记忆确认卡片

卡片显示：

```text
系统识别到你可能希望保存：……

保存范围：
○ 仅当前会话
○ 个人长期记忆
○ 当前项目

类别：……
有效期：长期 / 指定日期

[确认保存] [不保存]
```

如果用户显式说“记住”，但内容属于一次性要求，确认卡片默认只推荐“仅当前会话”。这种内容不得再出现在“值得保存为跨会话记忆”的自动候选列表中。如果是“无记忆对话”或真正的临时对话，卡片应直接说明不能保存，并禁用确认按钮。

### 15.4 统一待确认记忆中心

显式“记住”意图、会话上下文提升和自动发现产生的 `memory_proposal(status=pending)` 集中展示在“待确认记忆”区域，而不是混入正式记忆列表。即时确认卡片只是该中心的快捷交互，不是第四套临时数据。

每条候选显示：

```text
候选内容
系统为什么识别它
候选来源
来源会话和原始消息
推荐类别
推荐范围
```

用户操作：

```text
确认并保存
编辑后保存
忽略
以后不再提示同类内容
全部确认（仅用于旧数据迁移批次，并二次确认）
全部忽略
全部删除
```

候选区域必须明确提示：

```text
以下内容尚未成为长期记忆，确认前不会用于其他会话回答。
```

### 15.5 记忆管理页

支持：

- 按类型、范围、项目和状态筛选；
- 搜索记忆；
- 查看来源；
- 查看修订链；
- 编辑；
- 启用或停用；
- 删除；
- 查看被哪些新记忆替代；
- 查看在哪些回答中被使用过。
- 单独查看和批量处理自动发现的待确认候选。

### 15.6 项目规则与目标管理

记忆管理页增加两个明确入口，不能只依赖通用记忆编辑弹窗隐藏这些能力。

项目规则管理：

- 只展示当前用户有权访问项目中的 `project_rule`；
- 支持创建、编辑、启用、停用和查看修订历史；
- 明确显示所属项目和“项目绑定后确定性注入”；
- 删除或停用后，后续请求不得继续注入；
- 项目未绑定时不得因为问题文本碰巧包含项目名而读取规则。

目标管理：

- 展示个人目标和项目目标；
- 支持将目标设为 `active / paused / completed / abandoned`；
- 显示目标范围、所属项目、来源、更新时间和当前进度状态；
- 只有 active 目标可以进入当前目标上下文；
- 状态切换必须保存审计信息，不能通过删除目标伪装成“已完成”。

### 15.7 会话级个人偏好开关

会话设置中增加：

```text
读取个人偏好：开 / 关
```

该设置保存到会话，不是只存在前端本地状态：

- 普通会话默认开启；
- “无记忆对话”默认关闭；
- 关闭后，该会话后续请求都不注入个人偏好；
- 重新登录、刷新页面和从历史列表重新进入后仍保持原设置；
- 单轮“本轮不使用跨会话记忆”仍可进一步临时关闭，但不能修改会话持久设置；
- 界面必须同时说明“消息仍会保存”和“是否读取个人偏好”，不能把两者混为无痕模式。

## 16. 异常降级和可观测性

记忆系统故障不能阻断正常聊天，但不能静默失败。

### 16.1 降级顺序

```text
完整记忆上下文
      ↓ 召回失败
个人偏好 + 会话摘要 + 最近消息
      ↓ 摘要失败
最近原始消息
      ↓ 历史读取失败
当前问题直接回答
```

### 16.2 用户提示

普通用户不需要看到技术异常，但可以在回答下方看到：

```text
本轮记忆服务暂时不可用，已使用最近聊天记录继续回答。
```

### 16.3 结构化日志与可选指标

当前仓库没有独立指标后端，本阶段不要求额外建设 Prometheus、StatsD 或监控平台。以下字段首先以结构化日志落地，每条日志具有固定事件名和可检索的 `stage`；未来接入指标系统后，再把队列长度、耗时和失败数量提升为指标。

至少记录以下结构化字段：

```text
context_build_duration
summary_duration
summary_input_tokens
summary_output_tokens
recall_duration
recall_candidate_count
recall_result_count
context_total_tokens
memory_degraded_reason
model_queue_wait_duration
model_queue_depth
model_request_priority
model_request_timeout
model_resource_pool：llm_generation / embedding
embedding_queue_wait_duration
embedding_request_duration
embedding_request_timeout
```

异常日志必须带：

```text
user_id（可脱敏）
request_id
conversation_id
message_id
stage
exception_type
```

不得把完整私密记忆内容直接打印到普通日志。

验收时必须能够通过日志检索回答：一次请求在哪个阶段降级、等待模型多久、使用哪个资源池、摘要是否成功、召回多少条以及最终为何失败。没有监控大盘不阻塞交付，但日志字段缺失、无法关联同一请求或只能靠自然语言猜测阶段，均视为未完成。

### 16.4 鉴权与数据隔离

所有记忆与上下文接口必须从登录身份解析 `owner_id`，不得信任请求体或查询参数传入的 `user_id`。以下资源都属于用户私有数据：

- 正式记忆和修订历史；
- `memory_proposal` 候选及其确认、拒绝、删除操作；
- 会话上下文状态与摘要；
- 助手消息 metadata 中的 `memory_usage_manifest`；
- 会话级忽略列表及项目绑定。

接口必须统一拒绝未登录、令牌过期和已禁用用户。读取或修改资源时同时校验资源所有者、会话所有者和项目权限；不能先按资源 ID 查询并返回内容，再做用户判断。跨用户访问统一返回不泄漏资源是否存在的错误响应，并保留安全审计日志。

## 17. 数据迁移要求

升级不能丢失现有数据。

迁移原则：

- 现有原始消息全部保留；
- 现有会话摘要可以作为旧版本摘要导入；
- 现有摘要的覆盖位置能够保留则保留，无法确认时标记为需要重建；
- 现有个人偏好继续有效；
- 现有长期记忆补齐状态、版本和来源字段；
- 现有停用、过期和替代关系不得被重新激活；
- v14/v15 已完成的迁移逻辑和数据结果应保留，不得重复重建；
- v16 补齐 `context_start_after_message_id`、`version`、`completed_items`、摘要执行状态和必要索引，用于第一阶段正确性修复；
- v16 对旧异常摘要使用确定判据：`summary != '' AND summarized_message_id IS NULL` 视为“保留了摘要文本但覆盖位置不可确认”，标记 `needs_rebuild=true`；不得猜测覆盖位置，也不得立即删除旧摘要；
- v17 新增 `memory_proposal` 及候选去重、来源和正式记忆关联字段，同时为正式记忆补齐 `confirmed_at`、`confirmation_source`，用于第二阶段候选统一和确认审计；
- v18 为目标补齐 `goal_status`，为会话补齐持久化的 `use_personal_preferences`，用于第三阶段目标管理和会话级偏好控制；
- 条目级来源、锁定和状态采用结构化 JSON 还是独立表由实现者选择，但迁移后必须保留用户已锁定内容；
- `confirmed=true` 的自动提取记录保留 active；
- 所有 `source=auto_extract AND confirmed=false` 记录统一复制到 `memory_proposal(status=pending)`，旧正式记忆行停用或标记已迁移，不尝试根据不完整的历史修订记录猜测其是否被用户编辑；
- 迁移过程应保存旧记录与新候选的映射，保证幂等执行，不能重复创建候选；
- 待确认中心提供全部确认、全部忽略、全部删除和逐条编辑复核能力；
- 迁移完成后，用户在编辑器保存正式记忆必须显式记录确认状态、确认时间和确认来源；
- 既有 `long_term_goal` 和 `todo` 在无法判断进度时默认迁为 `goal_status=active`；原本已停用的记录保持停用，不能因迁移重新召回；
- 既有普通会话的 `use_personal_preferences` 默认迁为 true，既有“无记忆对话”（原 temporary 标记）默认迁为 false；
- 旧的会话忽略记录继续生效；
- 临时会话不得在迁移后突然成为长期记忆来源。

首次运行不应对所有会话立即调用模型重建摘要。只在用户重新进入会话或会话再次产生消息时按需升级。

## 18. 建议实施顺序

### 18.1A 平台基础协调：当前单进程部署

该交付与第一阶段 A 并行，不阻塞上下文正确性和规则摘要修复：

1. 建立 `LLM_GENERATION` 与 `EMBEDDING` 两类资源池；
2. 将意图路由、聊天、知识库回答、Agent、学生研究和导师审核的实际 LLM 调用接入生成池；
3. 使用进程级共享容量控制强制 LLM 生成并发数为 1；
4. 在 ChatModel/模型客户端最终调用层设置唯一获取点，外层路由、Service、Agent Run 和 LangGraph 节点禁止重复加锁；
5. 覆盖 FastAPI async、`run_in_threadpool` 和 LangGraph/Agent 线程路径，不能只保护单个事件循环；
6. 锁具有获取超时，并在 `finally` 中可靠释放；嵌套获取明确禁止或实现调用上下文级可重入计数；
7. 启动时自动验证当前为受支持的单 worker 模式，不支持的多 worker 配置直接拒绝启动；
8. 以结构化日志记录等待、开始、结束、超时和失败，不要求本阶段建设独立监控系统。

Embedding 池的独立限流从本阶段移到第四阶段。本阶段只在架构中保留 `EMBEDDING` 资源分类，不改造知识库入库和 FAISS 查询链路，也不让它阻塞记忆上下文交付。

### 18.1B 平台高级调度：随第四阶段交付

以下能力在启用自动 LLM 摘要或允许多 worker 部署前完成，不是第一阶段 A/B 的前置条件：

1. 前台交互请求与后台任务的优先级队列；
2. 后台任务短超时、排队取消和调用级状态追踪；
3. 已开始且不可可靠取消的模型请求不强行抢占；
4. 多 worker 部署所需的跨进程并发协调；
5. 后台摘要运行时新前台请求的最大等待时间验收；
6. 高级调度完成前自动 LLM 摘要保持关闭。

### 18.2 第一阶段 A：上下文正确性与规则摘要

1. 执行 v16 迁移，补齐 `context_start_after_message_id`、`version`、`completed_items`、摘要来源和执行状态等字段；
2. 定义统一 `ContextPackage` 和上下文构建器，让普通聊天、知识库对话和 Agent 从同一份数据生成 Prompt；
3. `ContextPackage` 从一开始就包含生成使用清单所需的消息 ID、摘要版本、偏好和召回记忆快照，避免下一阶段重新查询或重写三条链路；
4. 对齐摘要覆盖范围与最近消息窗口，消除历史空洞和重复；
5. 知识库对话改为从数据库读取最近历史；
6. 用户编辑上下文时保留 `summarized_through_message_id`；
7. 重置时写入 `context_start_after_message_id`；
8. 用确定性结构化摘要替换原文追加截断，支持主题、目标、确认、约束、待解决、已完成、否定、替换和去重；
9. 由 `ContextPackage` 计算唯一历史分界，旧 `HISTORY_LEN` 只作为最小轮数，`SUMMARY_THRESHOLD` 只作为摘要触发阈值；
10. 第一阶段使用默认 6000 字符的可配置最近历史上限，超限优先移除最旧完整轮次，并保证被移除内容已进入摘要；
11. 超限时淘汰最旧低价值摘要内容，始终保留最新有效结论；
12. 当前消息与会话约束冲突时，本轮立即采用当前消息，并更新对应结构化槽位；冲突提示属于可选交互，不是阻塞要求；
13. 使用乐观锁保护摘要、覆盖位置和版本的原子更新。

### 18.3 第一阶段 B：真实使用快照与前端可见性

第一阶段 A 与 B 属于同一个大阶段，连续交付。A 建立唯一的 `ContextPackage`，B 只把其中已经用于 Prompt 的数据固化为 manifest，禁止在三条旧链路分别做临时快照：

1. 从 `ContextPackage` 生成 `memory_usage_manifest`；
2. 在模型调用进入队列或直接开始模型调用前保存到对应助手消息 metadata；
3. 通过 SSE 绑定到对应回答，历史会话直接读取快照；
4. 按 `prepared / queued / started / partial / cancelled / failed / completed` 更新生成状态；
5. 聊天停止、超时、路由失败和流式中断时保留快照并显示准确文案；
6. Agent 完成、失败、取消和恢复时合并 metadata 并保留 manifest；
7. 提供会话上下文状态接口，支持前端展示摘要类型、覆盖位置和执行状态；
8. 流式生成器维护帧/文本累加器，取消、异常和 `finally` 路径复用统一聚合逻辑写入 `response` 与 `generation_status`；
9. 上下文构建器根据消息 metadata 为非完整回答注入 `[未完成回答]`，因为历史查询本身只返回 query/response/metadata；
10. 摘要、完成事项和长期候选排除未完成回答，用户下一轮仍可以基于它“继续”；
11. 增加独立 SSE 元数据事件，并修复 React、Streamlit、Agent、RAG 和非流式消费者的兼容处理；
12. 非流式最终响应块 metadata 携带 manifest 与最终生成状态；
13. 对 manifest、上下文状态和消息读取补齐鉴权与跨用户隔离。

### 18.4 第二阶段：统一待确认候选和确定性迁移

1. 新建 `memory_proposal` 及 `pending / accepted / rejected` 生命周期；
2. 统一显式记忆意图、会话上下文提升和 `auto_extract` 三类候选来源；
3. `auto_extract` 只创建候选，不再写入可召回的正式记忆；
4. 用户确认时创建正式记忆或写入当前会话上下文，并建立关联；
5. 用户在正式记忆编辑器保存时写入 `confirmed=true`、`confirmed_at` 和 `confirmation_source=user_edit`；
6. 所有旧 `auto_extract + confirmed=false` 统一迁为 pending 候选并停用旧行，不猜测无法验证的历史编辑；
7. 提供全部确认、全部忽略、全部删除及逐条编辑复核；
8. 一次性内容直接从跨会话候选中剔除；
9. 当前消息临时反驳历史记忆时只影响本轮回答，`auto_extract` 不得自动修改、替代或新建正式长期记忆；
10. 完成统一候选中心、确认、拒绝、防重复提示以及完整鉴权测试。

### 18.5 第三阶段：项目边界、产品语义与关键词过渡修复

1. 删除 `_mentioned_project_names` 的静默项目记忆召回；
2. 支持显式项目绑定或“是否切换项目”的确认交互；
3. 项目规则在项目绑定后确定性注入，项目决策和结论再按相关性召回；
4. 更新依赖旧项目名召回行为的自动化测试；
5. 将“本次不使用”改为“在当前会话中不再使用”；
6. 保留“本轮不使用跨会话记忆”的单请求语义；
7. 将当前“临时对话”改名为“无记忆对话”，明确其仍持久化；
8. 执行 v18，增加 `goal_status` 和会话级 `use_personal_preferences`；
9. 增加项目规则管理和目标管理界面，支持项目规则启停及目标 active/paused/completed/abandoned 状态切换；
10. 普通会话默认读取个人偏好，“无记忆对话”默认关闭，并提供持久化的会话级开关；
11. 在不增加新依赖的情况下完成 §9.3.1 全句候选、停用词、完整主题词、可配置上限和权重修复。

### 18.6 第四阶段：模型预算、LLM 摘要与正式召回升级

1. 增加每个模型的上下文长度、Token 估算方法和安全余量配置；
2. Token 预算第一版采用保守字符估算，并在 manifest 标记 `budget_source=estimate`，不能伪装成精确 tokenizer 结果；
3. 复用平台模型调用协调器，不允许摘要模块绕过队列；
4. 完成 §18.1B 的前台/后台优先级、取消和调用状态追踪；只有产品确实启用多 worker 时才实现跨进程协调，否则继续明确限制单 worker；
5. 继续默认使用第一阶段已经完成的规则结构化摘要；高级调度通过验收前，自动 LLM 摘要保持关闭；
6. 接入模型结构化摘要时补齐排队状态、成本、解析失败保护和旧摘要保护，并在界面标为“模型摘要”；
7. 为 Embedding 查询、文档入库和未来记忆向量化建立独立限流池；
8. 完成中文分词与 BM25 的依赖选型和部署验证；
9. 对 BGE-M3 做吞吐和延迟基准测试后，再决定是否默认启用向量召回；
10. 接入多路召回融合、轻量重排和效果评测集。

### 18.7 后续独立阶段：真正的临时对话

1. 临时会话存储；
2. TTL 清理；
3. 退出即删除；
4. 与普通会话、“无记忆对话”和单轮关闭记忆明确区分。

## 20. 完成标准

本项目采用分阶段交付。每一阶段满足以下条件即可独立验收、提交和推送：

1. 本阶段功能闭环完成；
2. §19.14 中属于本阶段的阻塞用例全部通过；
3. 所有此前阶段的阻塞用例继续通过；
4. 本阶段未实现的后续能力在界面和文档中不得伪装成已经完成；
5. 防御性用例和后续阶段用例失败不能被隐瞒，但不阻塞当前阶段交付。

完成所有计划阶段后的总体标准如下：

1. 任意时刻都不存在“既不在摘要、也不在最近原文”的历史空洞；
2. 智能聊天、知识库对话和 Agent 使用同一套上下文构建规则；
3. 摘要是可持续更新的结构化压缩，不是原文拼接；默认规则摘要能够处理确认、否定、替换和完成状态，启用 LLM 后升级为模型语义摘要；
4. 重置后旧内容不会自动恢复；
5. 用户编辑不会导致历史重复摘要；
6. 会话摘要不会未经确认自动成为长期记忆；
7. `auto_extract` 只写入独立的 `memory_proposal`，确认前不创建正式记忆且永不进入模型 Prompt；
8. 项目记忆和用户记忆严格隔离，项目名子串不能触发静默召回；
9. 每条回答展示的记忆就是生成时实际使用的记忆；
10. 知识库事实始终由当前检索文档支撑；
11. 当前功能以“无记忆对话”如实展示；真正临时对话上线后，其存储行为与界面承诺一致；
12. 记忆模块失败时聊天可以降级继续，并且故障可被定位；
13. 当前已启用能力对应的人工验收用例全部通过；尚未启用的后续能力按 §19.14 明确标记，不阻塞此前阶段。
14. 所有 LLM 生成调用进入统一生成池并遵守全平台并发数为 1 的限制；Embedding 使用独立限流池，前台问答不被自动摘要抢占；
15. 三类候选入口统一管理，同时保留明确的来源和不同交互优先级；
16. 已确认的正式记忆保持有效；无法证明已确认的旧自动记忆统一转为待确认候选，并提供低成本批量复核；
17. Agent 和聊天的完成、失败、停止、取消及恢复路径都保留生成时的上下文快照及 manifest，并准确区分模型是否已经启动；
18. 候选、上下文状态和 manifest 均通过登录身份完成所有权校验，未登录、令牌过期、禁用用户、跨用户访问和 `user_id` 伪造均不能绕过；
19. 用户档案、项目上下文、项目规则和目标虽然可以共享持久化设施，但使用不同的作用域、注入和生命周期策略；
20. 半截回答能够恢复查看和支持“继续”，但始终以未完成状态进入上下文，不会被摘要或候选当成已完成结论；
21. 新增 SSE 元数据事件不会在 React、Streamlit、RAG、Agent 或非流式消费路径中污染回答正文；
22. 项目规则和目标具有可操作的管理界面，目标可以切换 active/paused/completed/abandoned；
23. 普通会话与“无记忆对话”的个人偏好开关具有明确默认值并持久化到会话；
24. 当前阶段使用结构化日志完成可观测性，不以建设独立监控平台作为记忆功能交付前提；
25. 第一阶段通过统一历史边界和保守字符预算同时保证无历史空洞与 Prompt 不失控，旧 `HISTORY_LEN` 和摘要阈值不再各自决定窗口；
26. 模型生成容量只在最终模型客户端调用层获取，Agent 和 LangGraph 的嵌套执行不会重复加锁或自死锁；
27. 五层记忆开关具有统一优先级，下层只能收紧上层限制，前后端显示的生效状态一致；
28. 非流式响应与流式响应都返回生成时的同一份 manifest，不在回答后重新推算；
29. 旧摘要文本存在但覆盖位置为空时按明确判据标记重建，不猜测、不删除旧摘要。
