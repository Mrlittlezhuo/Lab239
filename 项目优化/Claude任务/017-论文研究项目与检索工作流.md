## 3. 背景

项目已具备用户体系、会话与长期记忆、智能意图路由、统一 LangGraph 智能对话、
Agent Run/Step、断点恢复与 Phoenix Trace，但还没有“论文研究项目”这一业务对象。
现在即使 Agent 搜索到论文，结果也主要停留在对话或工具输出中，不能作为一个
长期项目继续筛选、恢复和追踪。

用户明确要求把原计划的三项工作合并实施：

1. 研究领域数据基础与项目 CRUD；
2. 论文采集、元数据标准化和去重；
3. 可持久化、可取消和可继续的第一版论文研究 LangGraph 工作流。

本任务将它们作为同一个“研究项目到候选论文”后端业务闭环实现，但不将证据
提取、论文比较、报告生成和完整 WebUI 一并塞入本次。

## 4. 完成后的用户能力

在不依赖新 WebUI 的情况下，后端 API 至少应支持下列过程：

1. 当前登录用户创建私有研究项目，填写名称、研究问题和基本范围；
2. 系统生成可编辑的研究计划、子问题和检索式；
3. 用户确认后启动研究运行，从第一版可用来源检索论文；
4. 系统把不同来源的结果标准化、去重、筛选并持久化到项目；
5. 用户能查看候选论文，并将它们标记为待审、纳入或排除；
6. 用户刷新、重新登录或服务重启后，仍能看到项目、计划、运行状态和论文；
7. 执行失败、取消或暂停后可以从已持久化的阶段继续，不重复创建同一批论文。

## 5. 实施阶段

### 5.1 阶段 A：研究领域数据基础

在现有幂等迁移框架中追加新版本，并建立下列最小领域概念：

- 研究项目：所属用户、名称、研究问题、范围、状态、当前阶段和时间；
- 研究运行：所属项目、研究计划、检索式、阶段、状态、错误和关联 Agent Run；
- 论文记录：可全局复用的公开论文规范元数据；
- 项目论文：论文在某个项目中的来源、相关度、筛选状态、纳入/排除原因；
- 证据卡片和研究报告：只建立后续功能需要的最小归属与版本基础，本任务不生成其内容。

字段命名和拆表方式由 Claude 根据现有 SQLAlchemy/仓储风格合理设计，但必须保证：

- 项目、运行、项目论文、证据和报告通过项目归属到当前用户；
- 公开论文元数据可在项目间复用，但项目内的筛选、笔记和结论不共享；
- 用户私有上传文件不得因元数据复用而向其他用户暴露；
- 迁移对 v7 数据库幂等升级、保留旧数据，失败时不记录新版本；
- 不重建、不清空现有数据库或公共知识库。

提供研究项目的创建、列表、详情、修改和删除 API。所有归属判断从服务端认证
上下文获取用户，请求体中的 `owner_id` 不得成为授权依据。删除策略可采用与现有
项目一致的软删除或级联删除，但必须有清晰测试，且不得影响公共论文元数据。

### 5.2 阶段 B：论文采集、标准化与去重

建立集中的论文候选结构和来源适配层，不要让 LangGraph 节点直接解析各种工具的
自由文本输出。第一版至少复用两类已有能力：

- ArXiv 检索；
- 现有本地/公共知识库检索。

已存在的用户论文上传、网页搜索或 MCP 工具可通过同一适配接口接入，但本任务
不要重做下载器、知识库、通用爬虫或工具注册系统。某一来源不可用时，应记录该来源失败
并允许其他来源继续；所有来源均失败时才使本阶段失败。

标准化结果至少覆盖标题、作者、年份、摘要、DOI、ArXiv ID、稳定来源 URL、来源名称和
全文可用状态。去重应优先使用 DOI/ArXiv ID 等稳定标识，其次使用规范 URL，最后才使用
规范化标题和年份；要保留合并后的来源信息，不能因去重丢失可追溯性。

同一研究运行重试或恢复时，论文入库必须幂等，不得新增重复的论文记录或
项目论文关系。

### 5.3 阶段 C：第一版研究 LangGraph 工作流

在现有 Agent Runtime 和智能对话总图之上增加论文研究业务子图，其阶段语义至少包含：

```text
prepare_plan
  -> wait_for_confirmation
  -> retrieve_sources
  -> normalize_and_deduplicate
  -> screen_candidates
  -> persist_results
  -> completed
```

节点命名可按现有代码风格调整，但必须是真实的多节点 LangGraph，不得把全部流程
包装在一个节点或 API 的长 `if/else` 中。

关键约束：

- 研究阶段和产物写入数据库，不只保存在模型上下文或进程内存中；
- 计划生成可使用模型，但必须校验为结构化子问题与检索式，解析失败时有可控错误；
- 计划在执行前可被用户查看和修改，确认操作必须是服务端状态转换；
- 研究运行关联当前用户、研究项目和现有 Agent Run/Step，复用其时间线、取消和 Trace；
- 复用现有 LangGraph checkpoint/恢复机制，不建第二套 Agent 执行器或无关的任务队列；
- 过程内取消、来源部分失败、全部来源失败、重试和恢复均有明确终态或阶段语义；
- 运行完成后返回结构化摘要，包含各来源命中数、去重数、候选数和项目论文列表；
- Phoenix 开启时能通过研究项目 ID、研究运行 ID 和 Agent Run ID 关联研究子图、来源、
  去重与筛选 span；关闭或导出失败时不影响研究。

提供完成上述流程必需的 API，至少包括：生成/更新计划、确认并执行、查看运行、
取消/继续运行、查看项目论文、修改论文筛选状态。API 可根据现有路由风格合理
组织，不要为了满足固定 URL 而破坏现有结构。

### 关键设计选择

- 数据模型：`paper_record` 保存公开规范论文元数据（跨项目复用，DOI/ArXiv

  （`UNIQUE(project_id, paper_id)`，筛选状态/原因/相关度挂在这层）；
  `evidence_card`/`research_report` 本任务只建最小版本/归属基础，内容为空。
  删除项目级联只清私有产物，绝不触碰 `paper_record`。
- 去重键：DOI -> ArXiv ID -> 规范 URL -> 规范化标题+年份。批内去重
  （`dedup_candidates`）与跨运行去重（`upsert_paper` 查库合并）两级；
  合并保留全部来源（`sources_json` + `merged_sources`），补齐缺失字段但
  不覆盖已有值；`link_project_paper` 幂等且不重置用户已做的筛选。
- 研究图：真实 6 节点子图 `prepare_plan -> wait_for_confirmation ->
  retrieve_sources -> normalize_and_deduplicate -> screen_candidates ->
  persist_results`，阶段间条件边在终态/挂起时走 END。确认是服务端状态
  转换（原子 UPDATE `awaiting_confirmation -> running`），未确认的运行
  不会越过确认节点。检索逐来源逐检索式并先重读数据库取消状态；单来源
  失败记录统计继续，全部失败才 failed。筛选为确定性词元重合打分
  （第一版不调模型），全部候选保持 `pending_review` 交用户标记。
- 挂起/恢复：本机 Python 3.10 上 langgraph 1.2.14 不为 async 节点注入
  config 上下文（`ASYNCIO_ACCEPTS_CONTEXT` 仅 Python>=3.11），`interrupt()`
  在 async 节点必抛 `get_config outside of a runnable context`，因此挂起
  用"确认节点让本轮图正常结束 + 数据库 `awaiting_confirmation`"表达；
  确认/重试/崩溃恢复统一由运行时按 checkpoint 链尾处理：链尾有未完成
  节点则 `astream(None)` 重放（入库幂等保证不重复建论文），链尾已走完
  则重新进入图（计划已存库不重调模型，确认节点按数据库状态放行）。
  语义与 interrupt 挂起等价，且崩溃恢复与重试共用同一机制。
- 确认前编辑计划：确认节点放行时从数据库重读最新 `plan_json` 覆盖状态
  通道，保证检索使用编辑后的检索式（测试覆盖）。
- 恢复与 Agent Run 关联：不建第二套执行器。确认执行时创建一条
  `agent_run` 行（goal=研究项目名、plan_text=计划 JSON）并写入
  `research_run.agent_run_id`；研究终态同步到该行（completed/cancelled/
  failed 幂等映射）；重试新建一条"论文研究重试"关联行，旧行保持 failed。
  Phoenix 开启时业务 span 携带 `chatchat.research_run_id`、
  `chatchat.research_project_id`、`chatchat.agent_run_id`；关闭时 no-op。
- 命名调整：图状态类命名 `ResearchGraphState`、异常命名
  `ResearchConflict`，避免与任务 014 原型守卫（`test_langgraph_compat`
  禁止生产代码出现 `ResearchState`）冲突，守卫本身未改动。

  运行时间受来源超时约束；长任务的流式进度推送留给后续任务。
- `evidence_card`/`research_report` 只有表结构与归属字段，无内容生成
  （按任务范围属后续任务）。
- 挂起语义依赖"图正常结束 + 数据库状态"而非 langgraph `interrupt`：
  若未来升级到 Python>=3.11 且希望用 langgraph 原生中断/时间线 UI，
  需要把确认节点改回 `interrupt()`（节点内已留注释说明原因）。
- 运行中取消是"检索步骤边界检查点"粒度：来源调用进行中的取消要等
  当前一次来源调用返回后生效（无强制中断外部 HTTP 的能力）。
